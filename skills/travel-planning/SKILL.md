# 旅行规划

## 何时使用

用户要规划一次旅行、修改已有行程、加一天、换城市、调整节奏时使用。用户只是在问旅游问题或闲聊时正常回答，不要强行转成行程规划。

## 工具边界

| 工具 | 用途 | 使用要点 |
|---|---|---|
| `roam_get_snapshot` | 读本会话绑定的行程 | **任何编辑前先读一次**，面板上的改动可能已经覆盖了旧草稿 |
| `roam_prepare_draft` | 写入或替换整天行程 | 只写地点名，坐标交给宿主解析；终点站、城市名不要当作景点写 |
| `roam_search_places` | 高德 POI 检索，返回准确坐标 | 名称模糊、县级市、重名景点时**优先用它**拿坐标 |
| `roam_fill_routes` | 为已有 leg 补真实路线 | 只处理已定义但没有几何的 leg，不会凭空造路 |
| `roam_forecast` | 每天天气（按当天第一个地点） | 出发前 16 天内有效，超出返回空 |
| `roam_save_candidate` | 冻结成候选，交用户在面板审阅 | 每次给用户看方案前都应保存候选 |
| `roam_adopt` | 采用候选 | **只能由用户决定**，不要代替用户点采用 |
| `roam_mcp_tools` / `roam_mcp_call` | 外部数据源（铁路、小红书笔记） | 先 `roam_mcp_tools` 看参数，再 `roam_mcp_call` |

## 流程

1. **访谈**：先从对话和历史提取已知信息，不重复问。只追问影响硬约束的关键未知——抵离条件、同行者行动能力、总天数、必去体验。公共交通班次、营业时间、票价这类事实由助手查，不要推给用户回答。
2. **查证**：围绕用户的关键体验查证，比较候选地点的适合度。计划中的每个地点都要能回答「它改变了哪项选择、时间或费用」；查不到就明确标为待定，不要用无来源的名字占位。
3. **起草**：用 `roam_prepare_draft` 分批写入。先落地，再补 `roam_fill_routes` 和 `roam_forecast`。
4. **候选**：`roam_save_candidate`，然后用简洁中文说明安排、取舍、限制和费用，请用户在地图上确认。
5. **采用**：用户明确同意后才 `roam_adopt`。

## 地理编码：最容易出错的一环

- **每次调用都必须带 `city`**。不带会全国乱匹配（实测：趵突泉被解析到西安，芙蓉街到云南，大明湖到新疆）。
- **县级市不生效**（实测：`city=曲阜` 时孔庙落到安徽亳州）。遇到县级市，先用 `roam_search_places` 拿坐标，再把 `lat/lng` 直接传给 `roam_prepare_draft`。
- **重名景点会偏**（实测：青岛天主教堂被解析到 35 km 外的城阳）。凡是名字不唯一的地点，都用 `roam_search_places` 校验一次。
- **核对回执**：`roam_prepare_draft` 会返回每个名字解析出的坐标。和目标城市的经纬度差超过 0.5° 就是错的，必须修正后再继续。
- **不要一次塞太多新地点**：高德免费版有每秒查询数限制（会报 `CUQPS_HAS_EXCEEDED_THE_LIMIT`），一次 20 个以上容易整份失败。按城市分批，每批 3–9 个。

## 交通

- 城内相邻活动之间用 `walk` / `drive` 的 leg；**城际不要硬塞成 drive**，那会得到一条横穿省的公路线。
- 城际换乘写进当天说明，不写成 leg。相邻两天之间没有 leg 时，地图会自动用虚线连接，表示「示意，不是真实路线」。
- 没有真实轨迹的 leg 也会画虚线；告诉用户哪几段是示意。
- **门到门**才是有效时间：住处→车站、候车、车程、出站、到目的地，各段都要留。候车按 20 分钟、出站按 10 分钟起算，带行李或老人再加。
- 火车票用 `roam_mcp_call(railway, query_tickets)` 查，带上 `time_from` / `time_to` / `station` / `limit`，不要凭记忆写车次和时刻。

## 天气与体力

- 用 `roam_forecast` 取每天天气；山上和海边比市区低 5–8°C，按最冷的一处提醒用户。
- 每天只安排一个重体力项目（爬山、长时间徒步），前后留松。徒步路线的时间不要用导航时间：高德按公路算，泰山红门→中天门实际要 2.5–3 小时，导航只说 46 分钟。

## 吃住

- 用餐围绕当天活动区域选，写进日程并标 `category: food`；只罗列搜索结果的饭馆不算安排。
- 住宿按每天最后一个地点选区域，告诉用户「住哪一带」而不是某个具体酒店。酒店存在、位置方便，**不代表有房或已预订**，必须说清。
- 需要实时房源或口碑时，用 `roam_mcp_call(xhs, search_feeds)` 查笔记，或让用户自己确认。查不到就标注待定。

## 费用

- 按全体同行者算总额，覆盖交通、住宿、餐饮和计划内的必要体验。
- 区分查得的价格和估价，说明余量。未知价格不能填成 0，只有确实免费的才写 0。

## 与用户协作

- 面板上用户可以直接改：改名、改时间、调顺序、跨天移动、删除地点、按名字添加地点。所以**每次编辑前先 `roam_get_snapshot`**，不要用旧草稿覆盖。
- 修改已采用的行程会重新打开草稿，需要再次采用。
- 用户的偏好只对那一项有效，不要外推成对所有未核实条件的接受。
- 关键体验缺少可行性依据时先查证；查不到就准确说明并提问，不要编。
